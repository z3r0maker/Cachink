## 1. Details

### SEC-AUTH-01: sessions never expire (high, confidence high)

`serializeSession` signs `base64url(JSON(claims))`, and `parseSession` checks only the HMAC. No field is
time-bound. Consequences:

- A cookie captured once, from a shared shop PC, a proxy log or malware, is valid until
  `SESSION_SECRET` rotates, which logs out every user.
- `logout()` deletes the cookie in _this_ browser only.
- `member_role` and `business_id` are frozen at login. An owner who removes an admin, or downgrades them
  to viewer, does not take effect: `requireMember` trusts the cookie's rank. Membership is also never
  re-checked for pages. `currentSession()` reads only the business name.
- ASVS V3.3.1/3.3.2 (logout and timeout) and V3.2.x (tokens) fail.

The lightest fix that keeps ADR-061's "GoTrue replaces the issuer" seam: add `iat`/`exp`/`sv` (session
version) to the claims, store `session_version` on `business_members`, and have `requireSession`
reject anything expired or with a stale `sv`. One indexed lookup per request is cheap once
`business_members(user_id)` has its index (DB-IDX-02).

### SEC-AUTH-02: portal login (high, confidence high)

- **Enumeration by timing.** `if (!user?.encrypted_password) return WRONG` returns in about 1 ms for an
  unknown email. A known email pays a bcrypt cost-10 compare (about 60–80 ms). The identical message does not
  help. Fix: always compare against a fixed dummy hash.
- **No throttling.** Each call is an unauthenticated server action. Nothing limits online guessing per
  account or per IP, and B-17 as written (per-device bucket) will not either.
- **Credential store exposure.** For the query to work, `xangarro_app` needs `SELECT` on
  `auth.users.encrypted_password` for all users. On hosted Supabase the `auth` schema belongs to
  `supabase_auth_admin`, so this grant is also a deployment unknown (B-01). If it is granted, a single
  SQL-injection or query bug in the portal exposes every tenant's password hash. GoTrue removes both the
  grant and the bespoke code.
- No MFA option for owners, who control money-adjacent settings (operators, devices, future
  merchant payment keys under ADR-066). Consider optional TOTP for owners at least before N-43.

### SEC-DEV-01: activation brute force (high now; critical-class once C-14 lands as written)

Arithmetic with 2⁴⁰ ≈ 1.1×10¹² codes, at most one live code per business, and 48 h validity:

| Live codes (N) | Expected guesses to hit one | At 1,000 req/s |
| -------------- | --------------------------- | -------------- |
| 100            | 5.5×10⁹                     | ~64 days       |
| 1,000          | 5.5×10⁸                     | ~6.4 days      |
| 10,000         | 5.5×10⁷                     | ~15 hours      |

Today a hit also needs the email, and codes are bound to the email of the admin who generated them.
But `EMAIL_MISMATCH` confirms the code, and owner emails are often public (business pages, WhatsApp
Business). With C-14's `via:'qr'` the email check disappears for any caller who sets that field. The
table then shows the whole attack. Vercel's per-invocation cost is a weak brake, and nothing
alerts. A successful redemption is visible in the portal (B-12) and revocable, but by then the
bootstrap has already delivered the catalog, the clients (names and phones) and every operator's PIN hash
(SEC-DEV-03).

Recommended shape:

1. `/activate`: 5 failures per IP per 10 min, then exponential backoff. Also a global circuit breaker,
   for example alert and slow down above 100 failures/min across all IPs. Store the counters in Postgres, as B-17 already
   prefers.
2. Return one public refusal (`CODE_INVALID`) for invalid code and email mismatch. Keep
   `CODE_EXPIRED`/`CODE_USED` only once the email matched, as today.
3. QR (N-25/C-14): a **separate** pairing token. At least 128 bits, single use, TTL ≤ 15 min, minted on
   "Mostrar QR", and carried in `https://app.xangarro.mx/activar#t=…`. The fragment never reaches
   Vercel logs or Referer, and a GET or link preview never redeems it. The 8-char code plus email stays the
   manual fallback.
4. Purge redeemed or expired `activation_codes` after 90 days (DB-IDX-02).

### SEC-DATA-01: the unplanned second front door (high, confidence medium)

Nothing in the repo configures the hosted project's Data API. By default Supabase exposes `public`
over PostgREST and grants table privileges to `anon` and `authenticated`. Against that setup:

- **Anon key:** the JWT has no `business_id`. `current_business_id()` falls back to the
  `xangarro.business_id` GUC, which PostgREST clients cannot set, so the result is NULL and no rows are returned. This fails
  closed, but only by a two-step argument that nobody tests.
- **Device token:** `{aud:'authenticated', business_id, sub}` is HS256. If it is signed with the project JWT secret,
  which is the direction ADR-061 and B-01's `SUPABASE_JWT_SECRET` point, PostgREST accepts it. With no `role`
  claim it runs as the anon role, and RLS scopes it to the device's tenant. The device can then `DELETE FROM sales`
  (DB-RLS-01) or rewrite `users.pin_hash` over REST, which is everything `isPushable` exists to prevent.
- **A future GoTrue access-token hook** that adds `business_id` would turn every portal user's browser
  JWT into a direct REST credential in the same way.

The portal and the push API do not need PostgREST. Disabling it, or exposing only an empty schema, is
the simplest fix. Add a B-01 smoke test that calls `/rest/v1/sales` with the anon key and with a device token
and expects 401 or `[]`.

### SEC-PRIV-01: LFPDPPP (high, confidence high)

The 2025 LFPDPPP (DOF 2025-03-20; authority: Secretaría Anticorrupción y Buen Gobierno) requires an
aviso de privacidad before collection, a way to exercise ARCO rights (20 business days to answer,
15 to make it effective), disclosure of transfers, and, under ADR-064, the _bloqueo_ period before
deletion. Today the portal collects owner emails and passwords, and the app collects operator names,
client names and phones, and device models. Nothing points anyone to an aviso. Minimum launch set:

- An aviso integral at `/privacidad`, and a simplificado at signup, at the app consent screen and on the
  activation screen. List the processors (Supabase, Vercel iad1/US, Sentry, Facturapi, Stripe, the
  email provider) and the purposes: service, billing, CFDI, support.
- ARCO: a portal form plus a published email. Items land in the admin inbox (N-08) with the legal clock.
  Owners get "Descarga tus datos" (P-34 exporter), which covers portability.
- The role split: Xangarro is _responsable_ for owner and staff data, and _encargado_ for the
  merchant's customer data (clientes, operators). This belongs in the terms (L-05).
- Retention: error events and bug reports (SEC-FN-01), activation codes, `staff_audit_log`, server logs.

### SEC-SEC-01: the service role in the portal, by plan (high, confidence high)

`03-backend.md:20` lists `SUPABASE_SERVICE_ROLE_KEY` and `SUPABASE_JWT_SECRET` in the portal's env
layout, and `:97` routes billing writes through the service role. B-10 (`:180`) puts the Stripe webhook
at `/api/stripe/webhook` in the portal. Followed literally, B-01 and B-10 reintroduce exactly what
ADR-063 moved to `apps/backoffice`. The N-05 CI guard checks files, not the Vercel project's environment.
Amend the plan text now, before B-01 runs.

### SEC-DEV-03: NIP hashes and lockout (medium, confidence high)

ADR-072 accepted that a 4-digit bcrypt hash on a phone is guessable offline, for a coworker threat
model. Three things change that calculus:

1. `recoveryPasswordHash` is deprecated but still shipped. It is a stronger secret whose hash does not
   need to leave the server at all.
2. ADR-071's browser register stores the same hashes in OPFS, in the portal's origin, on possibly
   shared PCs. That strengthens SEC-WEB-01.
3. The lockout resets to zero after each 30 s cooldown and trusts `new Date()`, which a user can move
   forward to skip the wait.

### SEC-FN-01: `bug-report` (medium, confidence high)

The function predates Xangarro (Cachink ADR-025/027), but the app branch still wires it
(`EXPO_PUBLIC_BUG_INGEST_URL`, error outbox). Consent-gating on the device is correct
(`observability-bridge.tsx`), but the server accepts anything from anyone who holds the anon key.
That key is public by construction.

| Can fake locally                                                                                          | Cannot fake (server-enforced today)                                                                                                                            | Should be server-enforced before launch                                                                                                                                                                      |
| --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Plan, features, capabilities, record limits, staleness and grace clocks, the "lapsed" banner, PIN lockout | Tenant (the token is signed, and every call re-reads `devices` for revocation), device slots (B-12 row lock), which rows a push may touch (RLS + `isPushable`) | Operator limit (portal only today), `cobrosIntegrados` (intent API, ADR-066), Asesor and informe (portal), usage counters (ADR-065 "server is authoritative": computed on push, not trusted from the device) |

The signature's value is to stop a non-rooted user, or a network attacker, from editing the plan, and to
make tampering evident. It is not an enforcement boundary, and ADR-053 §5 does not claim otherwise.

## 3. Passes (SEC-INFO-01)

- **Tenant isolation in the portal.** All 8 server actions, `/api/export/[dataset]`, and `/api/v1/activate|entitlement`
  take the tenant from the signed cookie or device token, never from arguments, and run inside RLS
  (`withTenant`/`withSession`). The IDs actions receive (product, operator, device) can only match rows in
  the caller's tenant. I found no IDOR.
- **CSRF.** Next 16 server actions verify `Origin` against the host, the cookie is `SameSite=Lax` + `HttpOnly` (+
  `Secure` in prod), and `/api/v1/*` is bearer-only. The one cookie-auth GET (`/api/export`) is a
  download with no state change.
- **Open redirect.** Login has no return-URL parameter, and every `redirect()` target is a constant.
- **XSS.** No `dangerouslySetInnerHTML` in the portal. `build-comprobante-html.ts` escapes every
  interpolated field, and `rasterize.web.ts:72` injects only that output. The export uses ExcelJS
  string cells, so a leading `=` stays text.
- **Activation atomicity.** Single use is decided by one `UPDATE … WHERE redeemed_at IS NULL`. The
  slot count runs under a row lock. The code comes from `crypto.randomInt` with the alphabet derived from
  the contract regex. "Generar otro" expires the previous code.
- **Secrets in git.** Across 227 commits on all branches I found no live keys. I searched for
  Stripe `sk_/rk_/whsec_`, Supabase JWTs and `sb_secret_`, AWS, GitHub, Slack, Google, Sentry DSNs,
  `*.supabase.co`, PEM keys, and credentialed Postgres URLs. The only hits are dev/test material: the RFC 8032 keypair,
  `xangarro_app`/`postgres` local passwords, CI dummies, `sk_test_123`-style fixtures in CFDI tests,
  and public identifiers (EAS project id, Apple team id). `.env*` is gitignored.
- **Supply chain basics.** `pnpm install --frozen-lockfile` runs in CI. All 1,791 lockfile resolutions carry
  `integrity`, with no git or tarball sources. `onlyBuiltDependencies` limits install scripts to 4
  packages, and the `packageManager` field is hash-pinned.
- **Device token storage.** The token lives in `expo-secure-store` and never in SQLite (app branch).
- **Telemetry.** Sentry and the error outbox are opt-in (consent). A PII field blocklist runs in `beforeSend`. It
  does not scrub exception messages or console breadcrumbs, so keep domain error messages value-free.
  There is no analytics SDK in any package.
- **Admin console (N-05 branch).** The gate order is right: identity, then allowlist, then AAL2, and a stranger with
  2FA is still refused. `getClaims` verifies signatures. `requireStaff()` runs again inside actions.
  Mutations and their audit row share one transaction, and the audit table is append-only by grant. The per-request
  nonce CSP uses `strict-dynamic` with no third-party origins, plus `frame-ancestors 'none'`. HSTS preload,
  `noindex`, and `poweredByHeader:false` are set. No service role is used yet.
- **CFDI branch.** The PAC key is server-side only, the base URL must be `https`, the CSD is never in env, and
  idempotency keys are deterministic per Stripe invoice.

## 4. What I could not verify

- **Anything hosted.** B-01 is open, so there is no Supabase project, Vercel project or EAS production profile to
  inspect. That covers the Data API exposure (SEC-DATA-01), the `auth.users` grant on hosted, Supabase Auth
  settings for the admin project (signup disabled, password policy, JWT expiry, asymmetric keys),
  Vercel env vars, deployment protection on previews, WAF/rate limiting at the edge, and whether
  `bug-report` is deployed.
- **Live exploitation.** I did not stand up the portal or a disposable Postgres to exercise login timing,
  `/activate` throughput or PostgREST. The figures in SEC-DEV-01 are arithmetic, not measurements.
- **`/sync/push` and `/sync/pull`.** They exist only as **uncommitted** work in the main checkout
  (`apps/web/src/app/api/v1/sync/*`, `packages/application/src/apply-push`). I read the push route
  without auditing it. It authenticates the device, scopes by the token's tenant, and maps RLS 42501 to
  `DUPLICATE_CONFLICT` (DB-SYNC-05). One point for the re-run: last-write-wins on the **device-supplied**
  `updated_at` means a device can send a far-future timestamp and pin a HYBRID row (products) against
  later portal or device edits. Clamp it to server time or add a `server_seq` tiebreak.
- **The browser register runtime (ADR-071).** It is not built (O-02/O-06), so I could not review where the
  register keeps its device token, its CSP needs, or its OPFS exposure.
- **Stripe, Mercado Pago and Clip.** None is built, so SEC-PAY-01 audits the plan text only.
- **Mobile binaries.** I did no static analysis of a built IPA/APK (ATS/cleartext, exported
  components, `allowBackup` as generated by prebuild) and no check of `apps/mobile/plugins/*`
  beyond reading `app.json`.
- **Dependency reachability.** The `pnpm audit` triage is based on dependency paths, not a reachability analysis.
  The dev-only tree was not audited (`--prod` only).
- **ASVS L1 coverage.** V5 (input validation) was checked at the contract/Zod boundary only. V12
  (files) is not applicable until N-19. V9 (TLS) depends on hosting.
