## 1. Details

### DB-SYNC-01: the pull cursor loses rows (critical, confidence high)

`sync_log.seq` is `GENERATED ALWAYS AS IDENTITY`. Identity values are assigned when a row is
inserted, **not when its transaction commits**. The activation bootstrap already serves
`max(seq)` as the device's cursor, and B-09 plans `server_seq > since`.

Reproduced on the throwaway DB, as `xangarro_app`, tenant B…100:

| t   | Session A (slow portal edit)                      | Session B                         | Device pull                                                     |
| --- | ------------------------------------------------- | --------------------------------- | --------------------------------------------------------------- |
| 0 s | `INSERT sync_log` → seq **615101**, not committed |                                   |                                                                 |
| 1 s |                                                   | `INSERT` → seq **615102**, commit | `max(seq)` = **615102**, GAP-A visible = **false**              |
| 4 s | commit                                            |                                   | next pull asks `seq > 615102`, so **615101 is never delivered** |

The result is a portal edit (a price, an operator, a business flag) that silently never reaches a
phone. Nothing errors, and nothing retries. That is the "silent divergence" class of bug the system
is designed to avoid.

Fix options, in order of preference:

1. **A per-tenant counter under a row lock:** `UPDATE businesses SET last_seq = last_seq + 1
WHERE id = $1 RETURNING last_seq`, in the same transaction as the write. Writes then serialise per
   tenant, which is cheap (B-12 already locks the `businesses` row for activations), and commit
   order equals seq order within a tenant. It also removes the global sequence (ADR-053 §7),
   which helps partitioning and sharding later.
2. `pg_advisory_xact_lock(hashtextextended(business_id, 0))` before appending, keeping identity.
3. Keep the global identity, store `xid8` per row, and serve only `seq` below the first row whose
   `xid ≥ pg_snapshot_xmin(pg_current_snapshot())`.

Add a C-10 conformance test that interleaves two writers and a puller.

### DB-IDX-01: no tenant-leading indexes (high, confidence high)

> **Fixed 2026-09-22** — `drizzle/0033_tenant_indexes.sql` creates a
> `business_id`-leading index on all 43 RLS tables that carry the column, with the second column
> chosen per the set below (`fecha` for ledgers and cortes, `nombre` for catalogues, `seq` for the
> pull cursor); `celebraciones` and `sync_log` needed none (their primary key already leads with
> `business_id`), and `cfdi_globals` and `stripe_events` have no `business_id` at all. The
> declarations live in the Drizzle schema, so drizzle-kit stays in sync. Two guards, as this
> finding asked: `tests/tenant-indexes.test.ts` (static, no database) and
> `tests/tenant-indexes.integration.test.ts` (the `pg_index` query, run against a database).
> **Deviation:** the indexes are not partial on `deleted_at IS NULL` — a partial index only serves
> a query that repeats the predicate, and not every read filters soft deletes.

ADR-053 §7 and ADR-068 S1 make `business_id`-leading indexes binding "from today". The migration
creates exactly two. Every portal query therefore scans every tenant's rows and discards them in
the RLS filter. Measured at 200 tenants (§4): 24–169 ms before, 0.02–3.9 ms after. Seq-scan time
grows with **total** rows, not the tenant's own rows. Extrapolating linearly to ADR-068's ~36 M rows a year
gives roughly 3–15 s per dashboard query. The minimum set (§2.2) was measured with the tables
partial on `deleted_at IS NULL`. Add a CI test that queries `pg_index` and fails if an RLS-enabled
table lacks an index whose first column is `business_id`.

### DB-SYNC-02: planned sync columns are absent (high, confidence high)

03-backend B-02 step 2 plans `server_seq BIGINT` and `received_at TIMESTAMPTZ` on every synced table.
Step 4 plans `sync_log {…, device_id, received_at}` and `sync_rejections {…, client_seq, message}`.
B-03 step 4 plans `(business_id, server_seq)` indexes. None of these exist. B-09's
`acknowledged_through = MAX(server_seq) FROM sync_log WHERE device_id = …` cannot be written against the
current table. B-08's "upsert rejections by `(device_id, table_name, row_id)`" has no unique
constraint to target. The drift test's allow-list for `server_seq`/`received_at` is not needed yet, but
it will be the moment these land.

### DB-MIG-01 / DB-MIG-02: the migration path (high, confidence high)

- `drizzle/meta/_journal.json` has one entry (`0000`). `drizzle-kit migrate` would apply only the
  generated file, and never the RLS, the membership lookup or the redemption function.
- `db-local.sh apply_sql` runs `local/*.sql drizzle/*.sql` in glob order with no ledger. Its own
  header says it aborts on an already-migrated DB. That makes it fine for CI and fresh containers, but it
  cannot bring an existing database forward.
- `supabase db push` reads `supabase/migrations/`, which holds the **legacy** ADR-035 schema. Applied
  to a clean DB, it stops at line 240 (`AS $` is not a dollar-quote delimiter). Before that point it
  creates 10 tables whose shape conflicts with data-pg, plus a PowerSync publication. Its later
  `seed_business_on_signup` trigger would create a business for every `auth.users` insert.
  `0002_bug_database.sql` defaults its ids to `public.cachink_generate_ulid()`, which is defined in the
  broken block.

### DB-RLS-01: hard deletes are possible (high, confidence high)

`GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES … TO xangarro_app`, plus `ALTER DEFAULT
PRIVILEGES`, plus a policy without `FOR <cmd>`, together mean `DELETE FROM sales` succeeds for the
tenant. No code path does this today. The risk is that nothing stops a future one, and a deleted row
is invisible to devices, which only learn about changes through `sync_log` with `op ∈ {insert,update}`.
Soft delete is the model everywhere else (`deleted_at`). Revoke DELETE on the 18 synced tables and
`sync_log`/`sync_rejections`. Also consider `REVOKE UPDATE` on `sync_log` (append-only).

### DB-QRY-01 / DB-QRY-02: unbounded reads (high / medium, confidence high)

`periodLedger(tx, from, to)` ignores `from`/`to` in SQL (`entities.ts:96-108`). The period filter runs
in JS after `SELECT *` over all history, so the cost grows with the tenant's age. List screens and
exports have no `LIMIT` except `listMovimientosInventario` (50) and `recentActivity` (6). `shellCounts`
is fine: it counts in SQL.

### DB-RLS-02: predicate cost (medium, confidence high)

Same data, superuser, parallelism off, 400k-row `sales` seq scan: literal predicate 32 ms, the
policy's inline function **102 ms**, `(SELECT xangarro.current_business_id())` 32 ms (InitPlan once).
With the §2.2 indexes the predicate becomes an index condition either way, so the gap only shows on
scans. It is still a one-line change to the policy loop.

### DB-SYNC-03 / 04 / 05: push and pull design (medium, confidence medium; B-08/B-09 are not built)

These audit the **plan**, because `/sync/push` and `/sync/pull` do not exist server-side yet. Only
`/activate` and the contract mock do. They should be settled before B-08/B-09 are written.
DB-SYNC-04 in particular is a correctness bug in the plan text: truncating two tables at different
seqs and returning the larger seq skips the smaller table's remainder.

### DB-CHK-01: enum CHECKs (medium, confidence high)

The 30 enum columns are `businesses.tipo_negocio`, `categoria_venta_predeterminada`;
`employees.periodo`; `users.role`; `auditorias_inventario.estado`; `inventory_movements.tipo`;
`products.categoria`, `unidad`, `tipo`, `color_fondo`, `uso_producto`; `client_payments.metodo`;
`expenses.categoria`; `recurring_expenses.categoria`, `frecuencia`; `sales.categoria`, `metodo`,
`estado_pago`; `caja_movimientos.tipo`; `cancelacion_logs.metodo_original`; `day_closes.cerrado_por`;
`notices.source`, `severity`, `state`; `metas.objetivo`, `motivo`, `nivel`; `business_members.role`;
`devices.plataforma`; `sync_log.op`.

The push path validates rows with Zod through the contract. Portal actions, the seed, the admin
console (service role, N-05), imports (N-16) and webhooks do not all share that path, which is why this
is medium and not low. Derive the CHECK lists from the same `as const` arrays the Drizzle schema uses,
and assert equality in a test so the two cannot drift.

## 2. Recommended changes (to be implemented by the tasks named; not done here)

### 2.1 Migration rules (proposed B-20)

- One ledgered migration set that `supabase db push` applies. Hand-written files are journaled.
- Every migration file sets `SET lock_timeout = '3s'`.
- New indexes on tables over 100k rows use `CREATE INDEX CONCURRENTLY`, in their own
  non-transactional file.
- CHECK and FK constraints are added `NOT VALID`, then `VALIDATE CONSTRAINT` in a second step.
- Never `ALTER COLUMN TYPE` on `sync_log` or the transactional tables without a copy-and-swap plan.
- Old→new harness in `packages/data-pg/tests/migrations/`: apply migrations `0…N-1`, seed, apply
  `N`, and assert the data survives and the invariants hold.

Partition by `seq` range, or by `created_at` with PK `(seq, created_at)`. Better: shrink it first (DB-SYNC-03) and add retention or compaction. |
| `sales`                                   | ~2/3 of transactions                                              | yes                        | PK `id` alone. A partitioned PK/unique must include the partition key, so push's `ON CONFLICT (id)` needs a new target. `fecha` is text.                                                                                     |
| `inventory_movements`, `expenses`         | rest of transactions                                              | yes                        | same as `sales`                                                                                                                                                                                                              |
| `notices`                                 | Asesor feed, grows per tenant                                     | later                      | PK `id` alone                                                                                                                                                                                                                |
| `day_closes`, `caja_*`, `client_payments` | ~1/day/tenant                                                     | no (small)                 | —                                                                                                                                                                                                                            |
| catalogue and tenant tables               | bounded by plan limits                                            | no                         | —                                                                                                                                                                                                                            |

Points in favour: there are **no FKs** (FKs referencing partitioned tables complicate partitioning),
and every table already carries `business_id`.

Decisions N-51 must make:

1. **The partition key.** `fecha` gives pruning for portal reports. It is device-supplied and can be
   backdated. `created_at` is closer to immutable. Whichever is chosen must be immutable on update, or
   rows move between partitions.
2. **PK shape.** `(business_id, id, <partition key>)`, with push upserting on that target.
3. **Keeping `server_seq` ordering intact** (ADR-068): if the cursor is per-tenant (DB-SYNC-01 option
   1), ordering is independent of physical partitioning. With the global identity it must stay a single
   sequence across partitions.

Do DB-SYNC-01/02 and DB-TYPE-01 **now**. Each is cheap on an empty DB and a rewrite at 50 M rows.

### 3.2 What the N-07 capacity card should query

Run these as the admin/service role. `pg_stat_*` views are readable, but the numbers are estimates.

```sql
-- Trigger: DB > 25 GB (S2) / > 500 GB (S3)
SELECT pg_database_size(current_database()) AS db_bytes;

-- Trigger: any table > 50 M rows (use reltuples; exact count(*) is too slow at that size)
SELECT c.relname, c.reltuples::bigint AS approx_rows, pg_total_relation_size(c.oid) AS bytes
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public' AND c.relkind IN ('r', 'p')
ORDER BY c.reltuples DESC LIMIT 10;
-- After N-51 partitions tables, sum the partitions:
--   SELECT sum(c.reltuples) FROM pg_partition_tree('sales') t JOIN pg_class c ON c.oid = t.relid;

-- Trigger: > 10 000 active tenants (S3). Needs devices(last_push_at) or a usage_counters row (N-02).
SELECT count(DISTINCT business_id) FROM devices
WHERE revoked_at IS NULL AND last_push_at > now() - interval '30 days';
```

## 5. Backups and PITR: restore-drill runbook outline (not executed)

**What exists:** nothing in the repo. X-10 has one line ("Supabase PITR enabled on prod"). On Supabase,
daily backups come with paid plans. PITR is a paid add-on that needs a minimum compute size, so
confirm on the chosen plan. There are no hosted projects yet (B-01 is open), so nothing could be checked.

**Targets to agree** (proposal): RPO ≤ 5 min (PITR), RTO ≤ 2 h for the whole DB, and ≤ 4 h for a
single-tenant logical restore.

**Drill (run before N-30 beta, then quarterly; record the time of each step):**

1. **Prepare.** Choose a staging project with PITR on. Seed a known dataset and record per-table row
   counts, a per-tenant checksum (`sum(monto_centavos)`, `max(seq)`), and the current time `T0`.
2. **Damage.** At `T0 + 5 min`, simulate the incident: `DELETE` one tenant's sales as a privileged role,
   or drop a table. Note the exact damage time `Td`.
3. **Restore.** Use Dashboard → Database → Backups → PITR, target `Td − 1 min`. **Start the timer.**
   Record when the restore was requested, when the project was reachable, and when the portal was
   healthy again.
4. **Verify.** Compare row counts and checksums with step 1. Run the RLS suite (`test:db` against the
   restored DB). Check that `sync_log` `max(seq)` did not go backwards relative to what devices hold.
   If it did, devices have cursors ahead of the DB: run the **cursor-rewind procedure**, which forces
   `since=0` re-bootstrap for affected tenants, so write it as part of this drill.
5. **Single-tenant path.** PITR is whole-database. Practise restoring into a **new** project and
   copying one tenant's rows back with `COPY … WHERE business_id = $1`, under a privileged role,
   re-appending `sync_log`.
6. **Devices.** Confirm that devices re-push anything newer than `Td` from their outbox. UP rows are
   idempotent on id, so re-pushes are safe, and `acknowledgedThrough` means the phones have not purged it.
7. **Record** the timings, gaps and fixes in `docs/audits/db-restore-drill-YYYY-MM-DD.md`.
8. **Separately:** the dormancy archive (N-48) and "Exportar" are tenant-level exports, not backups.
   Also test that a PITR restore does not resurrect a tenant deleted after the dormancy export.

## 6. What I could not verify

- **`pg_stat_statements` on real traffic.** There is no hosted DB and no traffic yet. The extension
  was enabled on the throwaway DB, but a synthetic workload's top-N would be fiction. That part of
  N-27's scope moves to the pre-beta re-run.
- **Hosted Supabase posture:** the owner and BYPASSRLS of the SECURITY DEFINER functions
  (DB-RLS-03), whether Supabase's default grants to `anon`/`authenticated` interact with the policies
  (they have no `TO` clause), Supavisor mode (DB-CONN-01), and PITR availability or cost on the plan.
  B-01 is open.
- **`/sync/push` and `/sync/pull`.** They are not implemented server-side, so the push/pull findings
  audit the B-08/B-09 plan and simulated SQL, not real handlers. The push timing (P1) excludes
  Node↔DB round trips.
- **Scale beyond 200 tenants.** The Docker VM had ~3.3 GB free and was shared with other running
  containers, so I did not load a 7 M-row dataset. The whale tenant stands in for per-tenant growth.
  The at-scale figures (3–15 s seq scans, 33 s index build, 50 s rewrite) are **linear
  extrapolations**, not measurements.
- **Parallel query and hosted compute.** Timings are local arm64 Docker. Absolute numbers will differ
  on Supabase compute; the relative before/after holds.
- **The admin console (N-05) and service-role code paths.** They do not exist yet, so I could not list
  any service-role bypass sites. Today the only RLS bypasses are the two SECURITY DEFINER functions
  (`0002`, `0003`) and superuser connections, which the seed and CI apply step use.
- **The CLAUDE.md "one CorteDeDia per day per device" rule.** It is unenforced (no unique constraint).
  I could not tell whether it still holds after ADR-053, so DB-CHK-02 leaves it to the owner.
