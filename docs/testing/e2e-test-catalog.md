# E2E Scenario Catalogue — Xangarro!

> **Rewritten 2026-11-03 for the production cut.** The previous catalogue described the
> standalone Director app (wizard, roles, conversions, merma reports) that ADR-053 retired;
> every ✅ in it pointed at flows deleted in M-01/M-11. This version is derived from the specs
> and flows that exist on `main` today, journey by journey, across the three surfaces and the
> round trips between them. Re-derive the Status column from the suites before trusting it;
> `pnpm --filter @xangarro/web test:e2e` and `apps/mobile/maestro/scripts/full-regression.sh
--dry-run` are the sources of truth.

## 0. How to read this

**A scenario is one sentence a shop owner would recognise**, with the state it starts from and
what must be true at the end. Each journey below lists its happy path first, then the variants
that history says break products of this kind: **refusals** (the system says no and nothing is
written), **boundaries** (limits, last unit, end of month, 13 months), **interruptions** (offline,
reload, kill, second tab, session death), **concurrency** (two operators, two phones, two tabs,
double click), and **recovery** (retry, reconnect, re-pair).

| Column       | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Pri**      | **P0** blocks the production cut · **P1** first sprint after · **P2** nice to have                                                                                                                                                                                                                                                                                                                                                                  |
| **Layer**    | **PW** portal Playwright (viewport + serial projects) · **PW-op** the web caja (`operador` project, behind the real door) · **PW-sync** the `sync` project: phones simulated over HTTP against the real `/activate`, `/sync/push`, `/sync/pull`, plus the portal UI · **PW-con** backoffice Playwright · **M** Maestro on the iOS simulator against `pnpm mock:api` · **X** the X-02 manual runbook: a real build against a real backend on staging |
| **Status**   | ✅ automated and in a suite · ⚠️ one half only, or asserted indirectly · ❌ not automated · ⛔ the feature is not built (listed so the scenario is written when it ships; not a gap)                                                                                                                                                                                                                                                                |
| **Coverage** | The spec or flow that proves it. A spec name without a path is `apps/web/e2e/`; a `.yaml` is `apps/mobile/maestro/flows/`; `backoffice/` is `apps/backoffice/e2e/`.                                                                                                                                                                                                                                                                                 |

**What each layer can and cannot prove today** (this is why the same scenario can be ✅ on one
surface and ❌ on another):

- **Maestro runs the phone against the contracts mock, never against the portal.** The mock
  speaks the wire contract (C-10 conformance keeps it honest) and has seven scenarios
  (`xangarro`, `xangarrito`, `over-limit`, `grace`, `lapsed`, `revoked`, `flaky`) plus control
  routes (`/__mock/reset`, `/code`, `/qr`, `/forget`, `/restore`, `/scenario`,
  `/snapshot-budget`). It has **no «server down» control** and the iOS simulator has **no
  airplane mode and no camera**, so the phone's offline behaviour and the QR path are not
  automated anywhere.
- **The `sync` project is the only automated web ⇄ phone round trip.** It activates phones with
  `sync-phone.ts` and pushes rows over HTTP exactly as the app would, so it proves the server
  and the portal; it does not prove the phone's outbox, pull applier or UI.
- **The curated Maestro regression is 20 flows** (`full-regression.sh`), each from a fresh
  `activated` state; the other 24 flows in `flows/` run by hand with `run-flow.sh`. The
  `maestro-e2e` GitHub job is **dispatch-only**; nothing phone-side runs on a PR.
- **Playwright runs Chromium only, desktop 1440 / laptop 1024 / tablet 768.** No WebKit, no
  Firefox, no phone-width portal.

## 2. Suite shape and the rules that keep it honest

- **Layers, cheapest first.** Domain/application unit (every rule, 1 happy + 3 unhappy) →
  `data-pg` integration (every join the seed does not exercise) → contract conformance (mock
  and real backend answer alike) → Playwright per surface (real data reached the page: the
  sentinel rule) → the `sync` project (the server-side half of every chain) → Maestro (the
  phone's own applier, outbox and UI, against the mock) → X-02 (one real run per release
  candidate). A scenario is placed at the lowest layer that can observe its outcome; E2E is
  reserved for journeys and chains.
- **Every scenario names its state.** Playwright specs that write mint their own tenant
  (`mintTenant()`, ADR-128) or carry `@serial`; Maestro flows declare `# x-entrypoint:` and
  reset the mock scenario they changed. A flow that leaves the device in another state says so
  in its header (as `settings-desvincular.yaml` does).
- **Chains are written from the owner's side.** A J10 row is a `sync.spec` test that drives
  the portal UI and an HTTP phone; the phone-UI half is a Maestro flow against the same mock
  rows; X-02 joins them once per cut. Three files, one scenario ID in each header.
- **Variants, not duplicates.** When the web caja and the phone share a rule (short cash,
  cancel with reason, cierre motivo), the Maestro flow and the `operador-*.spec` carry the same
  J-id so a divergence is a diff, not a surprise.
- **Flake discipline.** Web-first assertions and `interact.ts` retries on the web; `extendedWaitUntil`
  on ids, never text, on the phone; `EXPO_PUBLIC_E2E=1` kills the particle animation; the FAB is
  parked; a flow that passes once and fails once is a harness bug until proven otherwise
  (`E2E-SESSION-NOTES.md` §3).
- **CI.** `portal-e2e` and `backoffice-e2e` gate every PR. `maestro-e2e` is dispatch-only and
  runs the curated 20; the goal for launch is a nightly on the iPhone runner with the suite
  going red on any failure, and the sync project's chains promoted to required.
