## 1. Project Overview

**Xangarro!** (`Cachink!` before ADR-054) — _"Finanzas para emprendedores."_ Financial control and micro-POS for Mexican emprendedores and small businesses: captures ventas, egresos and movimientos de inventario, and produces NIF-compliant financial statements and KPIs. **Not an ERP, not facturación, not a CRM.** Every feature justifies itself against _the less clicks, the most value._

**Market:** Mexico — MXN, Spanish (es-MX) only, NIF accounting, Mexican payment methods (Efectivo, Transferencia, Tarjeta, QR/CoDi, Crédito).

**The shape of the product (ADR-053).** The phone is **strictly the capture surface**: ventas, egresos, caja y turnos, stock and scanning — the work done on the shop floor, single-role, no Director build. **The web portal owns everything else**: identity, roles, business configuration, catalogue, dashboards, estados financieros and billing. The NIF and KPI calculations stay in `packages/domain` and both surfaces consume them — that shared domain is the single constraint that makes the split safe.

Product scope per surface lives in `docs/plan/` (`04-portal.md`, `05-app.md`, `03-backend.md`, `10-operador-design-changes.md`, `17-consola-crecimiento.md`), not here.

## 2. Non-Negotiable Principles

1. **UX simplicity is a feature.** Fewer fields, fewer clicks, fewer decisions. Every new input must justify itself. When in doubt, cut it.
2. **Offline never blocks capture, and data is never held hostage** (ADR-053 §5). The cloud is the backbone, but the device captures through an append-only outbox against a signed entitlement, with a payment grace and a separate offline-staleness clock. When both expire the app degrades to read-only **plus export** — never deleted, never locked.
3. **Code lives in exactly one place.** Duplication across platforms, modules or layers is a bug. If the same logic, component or type appears twice, consolidate it. This applies to docs too.
4. **Test-Driven Development is mandatory** for domain and application layers. Write the failing test first. No feature ships without tests.
5. **Layered architecture with hard boundaries** (§4). UI does not call the database. Domain knows nothing about React, Postgres, SQLite or sync.
6. **No God files.** Files over 200 lines and functions over 40 get refactored — enforced by ESLint (`max-lines`, `max-lines-per-function`, `complexity: 12`), not by good intentions.
7. **Always use the latest stable packages.** Verify the current version on npm before adding or upgrading. Never default to an older "known-safe" version.
8. **Money is never a float.** Integer centavos everywhere, `bigint` across the Postgres boundary. **Parse it, never assert it** — a `sql<bigint>` that lies about a driver's text return produced a `-$640,885,164,500.00` KPI (ADR-094).
9. **No silent breaking changes.** Migrations, sync-schema changes and repository-interface changes need a migration plan and a test exercising old → new data.
10. **This file is the contract, not a task list.** Progress lives in the plan; decisions live in ADRs.

## 3. Monorepo Map

pnpm workspaces + Turborepo. `apps/*` and `packages/*`; `archive/` is excluded from the workspace.

### Apps

| App               | What it is                                                                  |
| ----------------- | --------------------------------------------------------------------------- |
| `apps/web`        | The portal — the owner's web surface. Next.js App Router, Radix primitives, vanilla-extract over `@xangarro/tokens` (ADR-057). |
| `apps/backoffice` | Internal staff console, `admin.xangarro.mx` (ADR-063). Same stack. The **only** project that may hold the service-role key. |
| `apps/landing`    | Marketing site `xangarro.mx` — Vite + React, prerendered to static HTML (ADR-084). |
| `apps/mobile`     | The capture app (iOS/Android). Expo + React Native, Tamagui, SQLite via Drizzle. |

### Packages

| Package                  | What it is                                                                 |
| ------------------------ | -------------------------------------------------------------------------- |
| `domain`                 | Pure business logic — NIF, KPIs, money, entities. No React, no IO.         |
| `application`            | Use cases. Orchestrates domain + repositories. No UI, no direct DB access. |
| `data-pg`                | **Postgres** (Drizzle pg-core) — cloud schema, RLS, queries, migrations.   |
| `data`                   | **SQLite** repository interfaces + Drizzle implementations (the device).   |
| `contracts`              | API + wire contracts shared by phone and cloud (zod). No transport, no IO. |
| `auth-core`              | Passwords, sessions, throttles, TOTP (ADR-079/080). Storage via ports.     |
| `tokens`                 | Design tokens — colour, type, shape, shadow, motion. Zero dependencies.     |
| `ui`                     | Shared Tamagui components (mobile).                                        |
| `email`                  | Transactional email — Spanish React Email templates + sender adapters.     |
| `observability`          | Audit logging, error telemetry, health checks.                             |
| `sync`                   | Cloud sync for capture: API client, reference-data applier, outbox.        |
| `sync-lan`               | **Parked** (ADR-053 §6) — code stays, nothing mounts it.                   |
| `testing`                | Shared fixtures, in-memory repositories, contract factories.               |
| `config`                 | Shared ESLint, Prettier, TypeScript and Vitest configs.                    |

**Node ≥ 22, pnpm ≥ 9, TypeScript strict with `noUncheckedIndexedAccess`.** Version floors live in the root `package.json`, not here.

## 4. Layer Boundaries

**Portal and backoffice:**

```
packages/domain  →  packages/application  →  @xangarro/data-pg queries (take a `Tx`)
                 →  apps/*/src/server/*.ts   wraps them in `withTenant(businessId, tx => …)`
                 →  'use server' actions     the only write path from the client
                 →  presentational screens   no data access, no business rules
```

Every tenant query runs inside `withTenant`. **RLS is the enforcement, not application-level filtering** (ADR-053 §7): one database, one schema, `business_id` on every row.

**Phone:** `domain → application → packages/data` repositories → screens. Platform code stays in its app; shared code is in `packages/`.


**E2E** (Playwright, portal + backoffice) needs a live database:

```bash
pnpm --filter @xangarro/data-pg db:reset      # apply + seed; do this before a full run
pnpm --filter @xangarro/web test:e2e          # sentinels enforced; aborts without DATABASE_URL
```

The phone's E2E is Maestro — `apps/mobile/maestro/`.

## 6. Conventions

- **Strict TypeScript.** No `any`, `@ts-ignore` or `eslint-disable` without an ADR.
- **Money in centavos**, documented as such in JSDoc. Format only at the presentation edge.
- **`as const`** for constant objects, to preserve literal types.
- **Workspace imports** — `@xangarro/domain`, never a relative path across packages.
- **Migrations, never hand-written SQL** against a live schema. Postgres: `packages/data-pg/drizzle/`. SQLite: `packages/data/drizzle/migrations/`. Both keep a journal.
- **Tests:** Vitest + `node:assert/strict`. No Jest, Mocha or external assertion libraries.
- **React:** functional + hooks, no class components. Portal styling is vanilla-extract over tokens; the phone is Tamagui.
- **Design tokens only** in the portal — no hex literal, `rgba()`, radius, border width or font size written inline. `pnpm lint:design` fails on all five, and `DESIGN_CONTRACT.md` is generated, never hand-edited.
- **Option selectors:** ≤5 mutually-exclusive choices → icon + description cards, not a dropdown. Reserve `<Combobox>` for 6+ or unbounded lists.
- **Spanish (es-MX)** in the interface, copied from the design; code and comments in English.

### Test coverage requirements

- **Domain + application:** every entity and use case, minimum 1 happy path + 3 unhappy paths (§2.4).
- **Anything reading Postgres:** an integration test that builds the rows the seed does not. A broken join is invisible when no seeded row exercises it.
- **New portal screen, route or drawer:** a Playwright spec that asserts **real data reached the page**, not just that a heading rendered.
- **A portal spec that writes the seeded tenant** carries the `@serial` tag (ADR-103), which runs it once in the serial project after the parallel phase; whoever wrecks a seeded row restores it in a hook that runs on failure too, and a fixture a test consumes it re-makes. While the viewport projects run, Postgres refuses every write to that tenant — the rule is enforced, not documented.
- **Phone screens, tabs, modals and auth gates:** a Maestro flow in `apps/mobile/maestro/flows/`, using the shared subflows in `flows/shared/` — never inlined auth steps. Changing a testID or a nav path means updating every affected flow in the same change.

## 7. What NOT to do

- Do not use floats for money, or assert a database's return type instead of parsing it.
- Do not export untyped objects.
- Do not add a dependency without checking npm for the latest stable version.
- Do not write God files. 200 lines, 40 lines per function.
- Do not test UI behaviour with unit tests — Playwright for the web, Maestro for the phone.
- Do not commit a schema change without a migration test.
- Do not silently merge sync conflicts. Surface them inline.
- Do not read a tenant's rows outside `withTenant`.
- Do not write the seeded portal tenant from an untagged Playwright test (ADR-103).
- Do not re-baseline `.design-lint-baseline.json` upward to make a change pass.

## 8. Error Handling

- **Domain:** throw typed errors with a `code` and `message`. Never a generic `Error`.
- **Data:** catch DB errors, wrap in domain errors, propagate. Log centrally.
- **Application:** catch, emit a user-facing message, log.
- **UI:** show the error state; never swallow. Every list and report implements loading, empty, error and with-data.
- **Sync:** conflicts become UI events; fatal errors queue for retry and show status.
- **Tests:** every error path is tested — happy path + 3 unhappy paths minimum.

## 11. Debugging a Failed E2E Run

**Playwright** (portal, backoffice): the HTML report and traces are written under the app's `playwright-report/`. A sentinel failure means the page rendered but its data did not arrive — check `DATABASE_URL` and whether the seed still contains what the sentinel names.

**Maestro** (phone), in this reading order:

1. `e2e-reports/latest.json` → `runId`.
2. `e2e-reports/runs/<runId>/manifest.json` → the tests with `"status": "failed"`.
3. Per failure, in `runs/<runId>/tests/<flow>/`: `result.json` (failed step, probable cause), `screenshot.png`, `hierarchy.json` (what testIDs were actually on screen), `report.md`, and `commands.json` for the full trace.
4. Cross-reference `result.json.failedStep.id` against `hierarchy.json` — that tells you whether the app was on the wrong screen or the element was simply missing.
5. `pnpm e2e:report` opens the HTML report.
